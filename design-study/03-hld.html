High-level design (HLD)

HLD answers one question: what are the big parts, and how do they talk? It ignores classes and columns. It shows boxes, arrows and the reasons.

C4: zoom in step by step

Level 1  CONTEXT      Leave Management App   ← people and outside systems around ONE box
                      Employee Manager HR Admin ──► [LMS] ──► Email service ; [LMS] ··► Entra ID
Level 2  CONTAINER    web (Angular) ► api (ASP.NET Core) ► db (SQL Server) ; api ► mail
Level 3  COMPONENT    inside api: Endpoints → Use cases → Domain ; Infrastructure implements interfaces
Level 4  CODE         classes (LLD, next pages)

Why four levels? Different people need different zoom. A manager needs level 1; a new developer level 2 and 3. Interview line: "Context shows the system as one box with its neighbours. Container opens it into runnable parts. Component opens one container."

Containers of the LMS (animated request journey)

What to noticeThe employee waits only for steps 1 to 5. Slow things (email) are moved out of the request. That is the most common HLD idea: do the essential work now, the rest later, and never lose it.

Modular monolith: one app, clear rooms

┌──────────────────────── one deployable API ───────────────────────┐
│  People module   Balances+Policy   Leave module    Notify module   │
│  (Employee,      (LeaveType,       (LeaveRequest,  (Outbox,        │
│   Roles)          Balance, Ledger)  Day, Idemp.)    Processed)     │
│        borders = schemas people / balances / leave / notify / audit │
└──────────────────────────────┬──────────────────────────────────────┘
                               ▼  one SQL Server database
OptionGoodCostWhen to choose
Monolith (plain)SimplestBecomes a ball of mud without disciplinePrototype
Modular monolith (LMS)One deploy, one transaction, clear borders, can split laterBorders kept by discipline and testsDefault for one team and moderate scale
MicroservicesIndependent scaling, releases, teamsNetwork failures, distributed data, many pipelines, observability costMany teams, parts with very different scale or release speed
The honest cross-module exceptionApply leave must change request, balance and audit atomically. Splitting them into separate services would need distributed transactions. The repo's constitution allows one named Application-level store (ILeaveApplicationStore) to write across modules in one database transaction. That is a real reason to stay a monolith.

Layers: Clean Architecture

   Api ───────────────┐   endpoints, auth, config, wiring (composition root)
   Infrastructure ────┤   EF Core, SQL Server, outbox writer, SMTP, clock
                      ▼
   Application  ─────► Domain      use cases + interfaces   │  entities + business rules
   (depends on Domain)             (depends on NOTHING)

Dependency rule: arrows point inward. Domain never knows EF Core or ASP.NET. Payoff: the notice rule runs in a unit test with a fixed "today" and no database.
