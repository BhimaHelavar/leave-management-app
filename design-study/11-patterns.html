Monolith to microservices: decision flow

Do separate teams need separate releases?      no ─┐
Does one part need very different scale?       no ─┤
Is a part truly independent (own data)?        no ─┼─► stay a MODULAR MONOLITH
Can you afford ops: pipelines, tracing, on-call? no ─┘
               yes to several ─► extract ONE module first (the one with the clearest border), measure, then decide more
Cost of microservicesMeaning
Network failure modesTimeouts, partial failure, retries
Distributed dataNo cross-service transaction; sagas, eventual consistency
OperationsMany deployments, tracing, versioning of contracts

Sync or async?

Use sync (HTTP)Use async (queue)
The caller needs the answer now (balance, apply result)The work can finish later (emails, reports, accrual jobs)
Simple flow, low volumeSmoothing spikes, retries, fan-out to many consumers

Queue vs topic vs event: a queue delivers each message to one consumer (send this email); a topic gives each subscriber a copy (leave approved → payroll and calendar); an event is a lightweight "something happened".

Build vs buy and technology choice

For any tool ask: Does a requirement demand it? Can the team run it? What is the exit cost? The LMS added Redis and RabbitMQ only after the vertical slice worked, each behind an ADR. That order shows maturity.

Writing an ADR (architecture decision record)

Title:     12  Days are held at submit
Context:   Two pending requests could together promise more days than exist.
Options:   deduct at submit | deduct at approval
Decision:  deduct at submit
Why:       Available stays honest.
Trade-off: reject and cancel must restore days.
Revisit:   if HR wants "tentative" requests that do not block balance.
