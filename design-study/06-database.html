Database design

The database outlives the code. A good schema makes wrong data impossible to save, even when the code has a bug. This page walks from requirements to the 13 real LMS tables.

The 8-step recipe

The ER diagram (read from the middle)

          └─< Holiday                              
Employee ─< LeaveBalance >─ LeaveType              ─< = "one to many"

Back-office, id-only references:  OutboxMessage ─ ProcessedMessage ;  AuditEvent

Cardinality words: one-to-many (employee → requests), many-to-many (needs a link table; EmployeeRole links employee and role text), one-to-one (rare). PK = identifies a row. FK = points at another table's PK. UK = unique business key.

Table explorer (click a table)

Click a table.
House rules (apply to every table) One schema per module (people, balances, leave, notify, audit). PK int identity (or bigint for tables that grow without limit). Leave days are date; timestamps are UTC datetime2(3) named ...AtUtc. Enums are readable varchar + CHECK. Every FK is NO ACTION on delete: no cascades, no hard deletes. RowVersion on tables two people may edit.

Normalization in plain words

FormRuleBad exampleLMS fix
1NFOne value per cell; no repeating groupsRequest row with Day1, Day2, Day3 columnsLeaveRequestDay rows
2NFEvery column depends on the whole keyHoliday name stored in each requestName only in Holiday
3NFNo column depends on a non-key columnManager's name inside EmployeeOnly ManagerId; join to read the name
Normalise by default, denormalise on purposeTwo deliberate copies in the LMS: (1) LeaveRequestDay.EmployeeId (needed for the unique overlap index; the composite FK keeps it consistent); (2) LeaveRequest.DaysCount (a snapshot, so a later rule change never rewrites history). A senior says why a copy exists and what guards it.

Which rules does the database enforce itself?

Rule                      Enforced by                                      Code can still check it too
5  never below zero       CHECK (Available >= 0) on LeaveBalance            yes (guarded UPDATE)
11 half day = one day     CHECK (HalfDay='None' OR StartDate=EndDate)       yes (LeaveRules)
13 no overlapping leave   UNIQUE (EmployeeId, LeaveDate, Slot)              yes (pre-check for a nice message)
   rejected needs reason  CHECK (Status<>'Rejected' OR comment is set)
   audit never changes    DENY UPDATE/DELETE + trigger

Principle: defence in depth. Code gives friendly errors; constraints guarantee correctness under bugs and races. Rules that need today's date or the holiday list stay in the Domain because a CHECK cannot see them.

Data types you must justify

ChoiceWhy
date for leave days, datetime2 UTC for momentsA leave day means the same date for everyone; "submitted at" is an instant
decimal(5,1) for daysHalf days (0.5). Never float for quantities you compare
int identity keys, not GUIDSmall, fast joins, smaller indexes. Cost: guessable ids, so every endpoint checks ownership
varchar + CHECK for enumsReadable queries; the CHECK list must match the C# enum (test it)
rowversionCheap optimistic concurrency token
Why does LeaveRequestDay contain EmployeeId, which looks redundant?
A deliberate, guarded denormalization.
Why store DaysCount on the request instead of recomputing?
It is a snapshot (ADR 13).
