Low-level design (LLD)

LLD zooms into one box of the HLD and decides classes, methods, interfaces and rules. Goal: code that is easy to test, easy to change, and hard to misuse.

The LLD recipe

  1. Find the nouns in the requirements: Employee, LeaveType, LeaveRequest, Holiday, Balance.
  2. Find the verbs: apply, approve, reject, cancel, preview. These become use cases.
  3. Separate pure rules (need only inputs) from things that touch the world (database, clock, email).
  4. Put an interface in front of everything that touches the world.
  5. Model states (lifecycle) as an explicit state machine.
  6. Decide errors: rule failures are results; bugs are exceptions.

Pure rules: the best LLD trick

A pure function gives the same output for the same input and touches nothing else. The LMS rules are pure, so tests are fast and certain. The real C# (from WorkingDayCalculator.cs):

public static WorkingDayResult Count(DateOnly start, DateOnly end, HalfDay halfDay, IReadOnlySet<DateOnly> holidays)
{
    var slots = new List<LeaveSlot>();
    var singleHalfDay = halfDay != HalfDay.None && start == end;

    for (var date = start; date <= end; date = date.AddDays(1))
    {
        if (IsWeekend(date)) continue;          // Saturday/Sunday never count
        if (holidays.Contains(date)) continue;  // holidays never count (sandwich rule off)

        if (singleHalfDay) slots.Add(new LeaveSlot(date, halfDay == HalfDay.FirstHalf ? Slot.AM : Slot.PM));
        else { slots.Add(new LeaveSlot(date, Slot.AM)); slots.Add(new LeaveSlot(date, Slot.PM)); }
    }
    return new WorkingDayResult(slots, ...);   // DaysCount = slots * 0.5
}
Design insightDaysCount = Slots.Count * 0.5. The saved day rows and the number are computed from the same list, so they can never disagree. Good LLD makes the wrong state impossible to represent.

Rule order matters (fail fast, one clear error)

DateRange → YearCross → DatePast → HalfDayInvalid → DaysNone → NoticeShort → MaxConsecutive
   (cheap, date-only checks first)            (need holidays/clock later)

LeaveRules.FirstViolation returns the first failure, in a documented order, so the API and tests always agree. The numbers (notice days, max days) come from the LeaveType row, so an Admin can change them without code.

static readonly Dictionary<LeaveStatus, LeaveStatus[]> Allowed = new()

public bool CanMoveTo(LeaveStatus next) => Allowed[Status].Contains(next);

LLD practice: design a class for a new rule

Requirement: "Casual leave: max 2 requests per month." Where does it go?

  1. Add a nullable column MaxRequestsPerMonth on LeaveType (config, not code).
  2. Add MonthlyLimit to LeaveRuleViolation and a new check in LeaveRules, after MaxConsecutive.
  3. The count of existing requests needs the database, so add it to LeaveRuleInput (RequestsThisMonth), loaded by LeavePlanner through a reader interface.
  4. Test the pure rule with RequestsThisMonth = 2.
  5. Map the violation to code monthly_limit and HTTP 422.
NoticeNo endpoint, no EF code changed in the rule itself. That is what good LLD buys.
