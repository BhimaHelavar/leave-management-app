Case 1: Expense claim approval

Clarify: employees submit claims with receipts; manager approves up to a limit; Finance approves above it; payment is out of scope.

StepAnswer
RequirementsSubmit, attach receipts, 2-step approval by amount, reimbursement report. NFR: audit 100 %, receipts private, p95 400 ms.
Estimate2,000 employees × 6 claims a year = 12,000 a year ≈ 50 a working day. Tiny. Modular monolith.
StatesDraft → Submitted → ManagerApproved → FinanceApproved → Paid; also Rejected, Cancelled
TablesExpenseClaim(Id, EmployeeId, Total, CurrencyCode, Status, RowVersion), ExpenseLine(ClaimId, CategoryId, Amount, ReceiptId), ExpenseCategory(Code, DailyLimit, NeedsReceiptAbove), Receipt(Id, BlobPath, Sha256), ApprovalStep(ClaimId, Level, ApproverId, DecidedAtUtc)
DB rulesCHECK (Total >= 0); unique (EmployeeId, Sha256) blocks the same receipt twice; money as decimal(12,2) + currency code, never float
Hard problemsApproval route depends on amount (strategy by data: ApprovalRule table); receipts in blob storage with short-lived links; fraud: duplicate receipt

Case 2: Meeting-room booking

Clarify: 50 rooms, 30-minute slots, no double booking, recurring meetings later.

CREATE TABLE booking.RoomSlot (
  RoomId int NOT NULL, SlotStartUtc datetime2(0) NOT NULL, BookingId int NOT NULL,
  CONSTRAINT PK_RoomSlot PRIMARY KEY (RoomId, SlotStartUtc),       -- THIS is the overlap rule
  CONSTRAINT FK_RoomSlot_Booking FOREIGN KEY (BookingId) REFERENCES booking.Booking(Id));

A 90-minute booking inserts 3 rows in one transaction; if any slot is taken, the primary key fails and the whole booking rolls back (409). This is exactly the LMS LeaveRequestDay trick. SQL Server has no range "exclusion constraint" (PostgreSQL does), so slot rows are the portable answer.

Case 3: Ticket booking (high contention)

Clarify: popular concerts, 50,000 users hit "buy" at 10:00, seats must never be sold twice.

Browser ─► CDN (static) ─► API ─► Queue ("waiting room") ─► Seat service ─► SQL
                                          │
   Step 1 HOLD seat (atomic UPDATE ... WHERE Status='Available') with expiry 5 min
   Step 2 PAY (payment provider, idempotency key per order)
   Step 3 CONFIRM seat (Status='Sold') ;  timeout job releases expired holds
   Emails and PDFs: outbox → worker
UPDATE ticket.Seat
SET    Status = 'Held', HeldBy = @order, HoldExpiresUtc = DATEADD(minute, 5, SYSUTCDATETIME())
WHERE  EventId = @event AND SeatNo = @seat AND Status = 'Available';   -- 0 rows = someone else got it
ProblemAnswer
Spike of 50,000 usersWaiting-room queue, rate limiting, static pages on a CDN, scale API instances out
Never sell twiceAtomic conditional UPDATE + unique (Event, Seat); never check-then-write
Payment fails after holdHold expires; a job releases it; payment confirmation is idempotent
Charged but order not savedSaga / outbox with reconciliation; idempotency key per order
ConsistencyStrong for seats; eventual for "seats left" counters on the page

A fourth warm-up: URL shortener (12 minutes)

  1. Requirements: create short link, redirect fast (p95 < 50 ms), 100 M links, 10:1 read:write.
  2. Estimate: 100 M × 500 bytes = 50 GB. Redirects 1,000/s average.
  3. Data: Link(Code PK, LongUrl, CreatedAtUtc); code = base62 of a counter or random 7 characters with a unique constraint and retry.
  4. HLD: API → cache (hot codes) → database; CDN for popular redirects.
  5. Trade-offs: counter (predictable, needs a coordinator) vs random (collision retries); 301 (cacheable, no analytics) vs 302.
