Database deep dive

The topics that separate a mid from a senior: money-like counters, races, indexes, transactions and safe change.

1. The balance problem: ledger + guarded balance row

OptionStrengthWeakness
A Counter onlyFast, simpleNo history; two writers overwrite each other
B Ledger only (balance = SUM)Full historyCheck-then-write races; SUM gets slower
C Ledger + balance row (chosen)History + speed + DB refuses negativeTwo writes in step (one transaction + a reconciliation test)

The guard is one atomic statement: the condition and the change happen together, so nothing slips in between.

UPDATE balances.LeaveBalance
SET    Available = Available - @days
WHERE  EmployeeId = @emp AND LeaveTypeId = @type AND LeaveYear = @year
  AND  Available >= @days;      -- 0 rows changed = not enough balance

Balance demo (start Available = 8.0)

#EntryTypeDaysRequest
Available (balance row): 8.0   Ledger sum: 8.0  

Why days are held at submit: if days were only taken at approval, two pending requests could together promise more days than exist (ADR 12). The cost: reject and cancel must restore.

Reconciliation query (must return no rows, in a test and a nightly check):

SELECT b.Id FROM balances.LeaveBalance b
WHERE b.Available <> (SELECT COALESCE(SUM(e.Days),0) FROM balances.LeaveBalanceEntry e
                      WHERE e.EmployeeId=b.EmployeeId AND e.LeaveTypeId=b.LeaveTypeId AND e.LeaveYear=b.LeaveYear);

Deadlocks

Two transactions wait for each other's locks. Avoid by writing tables in the same order in every use case (LMS: request, days, balance, ledger, audit, outbox). If SQL picks you as the victim (error 1205), retry the whole transaction (up to 3 times).

3. Indexes: how to think

An index is a sorted copy of some columns with pointers to rows, like a book index. It makes reads fast and every write a little slower. Rule: add an index only for a query you can name.

Scan vs seek

Rows in table
Screen / jobIndexIdea
My requests (newest first)LeaveRequest(EmployeeId, StartDate DESC) INCLUDE(...)Covering index: answered without touching the table
Manager inboxFiltered LeaveRequest(StartDate) WHERE Status='Pending'Filtered index stays tiny: most requests are decided
Team overlapLeaveRequestDay(LeaveDate) INCLUDE(EmployeeId)Who is away on a date
Submit overlap checkUnique (EmployeeId, LeaveDate, Slot)One index = rule + fast lookup
Outbox workerFiltered OutboxMessage(Id) WHERE SentAtUtc IS NULLSmall however many were sent
Audit log(ActorEmployeeId, Id DESC), keyset paging on IdCursor paging stays fast on deep pages
Three traps1) SQL Server does not index foreign keys by itself (EF adds them by convention; check the migration). 2) A filtered index may be skipped if the filter value is a parameter; use a constant and check the plan. 3) Never index by guessing: run the query with SET STATISTICS IO ON, look for a seek, compare reads.

4. Paging: offset vs keyset

-- Offset: simple, slows on deep pages (reads and throws away 10,000 rows)
SELECT * FROM audit.AuditEvent ORDER BY Id DESC OFFSET 10000 ROWS FETCH NEXT 20 ROWS ONLY;
-- Keyset: remember the last Id; always an index seek
SELECT TOP 20 * FROM audit.AuditEvent WHERE Id < @lastId ORDER BY Id DESC;

5. Migrations and safe change

Expand ──► deploy code that writes both ──► copy old data ──► Contract (drop old column in a later migration)
safe: old and new code both work during the deploy; each step can be rolled back
  • Never edit an applied migration; add a new one. Read the SQL first: dotnet ef migrations script.
  • Reference data ships in migrations (HasData); demo people only in Development (DevSeeder).
  • Deploy migrations as a separate step with a powerful login; the running API user has only the rights it needs.

8. Practice SQL (LMS)

-- Who is away on 2026-11-10 in my team (manager id 3)?
SELECT e.FullName FROM leave.LeaveRequestDay d
JOIN people.Employee e ON e.Id = d.EmployeeId
WHERE d.LeaveDate = '2026-11-10' AND e.ManagerId = 3
GROUP BY e.FullName;

-- Approved days by leave type in 2026 (HR report)
SELECT t.Code, SUM(r.DaysCount) AS Days
FROM leave.LeaveRequest r JOIN balances.LeaveType t ON t.Id = r.LeaveTypeId
WHERE r.Status = 'Approved' AND r.LeaveYear = 2026 GROUP BY t.Code;

-- Employees with no manager (HR approves for them)
SELECT Id, FullName FROM people.Employee WHERE ManagerId IS NULL AND IsActive = 1;
