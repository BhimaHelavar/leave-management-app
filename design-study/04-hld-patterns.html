HLD patterns you can play with

Four patterns solve most "what if it fails?" questions in the LMS. Each has a demo: break it first, then fix it.

1. Outbox: never lose the email

Problem: saving a request and sending an email are two actions in two systems (database and mail). One can succeed while the other fails. Fix: save the request and an "email to send" row in the same database transaction. A worker sends later.

Weakness of outbox?Email arrives seconds later and can be delivered twice. Fix: make the sender idempotent (ProcessedMessage(Consumer, MessageId)).
Why not just use RabbitMQ directly?The broker and the database cannot share a transaction. The outbox guarantees the message exists only if the request was saved; the broker then delivers it. The LMS keeps the outbox and adds the broker later.
What goes in the payload?Ids only (requestId, employeeId), never names or emails (privacy).

2. Idempotency key: a double click must not hold days twice

Idempotent = repeating gives the same result as doing it once. GET and PUT are; POST is not. Networks retry, people double-click, so creating POSTs carry an Idempotency-Key. The server stores the key, a hash of the body, and the response.

3. Optimistic concurrency: two managers, one request

Problem: two people read the same request. Manager A approves. Manager B (stale screen) rejects. Without protection the last write wins and the days are restored for an approved request. Fix: every read returns a version (ETag from SQL rowversion); a write sends it back as If-Match. If it changed, the answer is 409 stale_version.

409 vs 422: 409 means "valid request, clashes with current state; reload may fix it". 422 means "the request itself breaks a rule; retrying never helps".

  • Stampede: when a hot key expires, 100 requests all hit the database. HybridCache lets one caller reload while others wait.
  • Invalidation: when HR edits a holiday, remove or update the key (or accept a short expiry).
  • Hard rule: a cache is an optimisation, never the source of truth.
