RPO (Recovery Point Objective): how much data you can lose. RTO (Recovery Time Objective): how long you can be down. Define both, then test the restore.

Scaling levers, cheapest first

1 Fix the query / add the right index         ← almost always the real answer
2 Cache hot, rarely changing reads            ← Redis / HybridCache
3 Move slow work out of the request           ← outbox/queue + worker
4 Scale the API OUT (more instances)          ← needs a STATELESS API (token in header, no server session)
5 Read replica for reports                    ← HR reports off the primary
6 Partition / archive big tables              ← audit, outbox
7 Split services or shard data                ← last resort; real cost

Statelessness is the key to scaling outThe LMS API keeps no session in memory: the JWT carries identity, the database holds state. Any instance can serve any request. (The dev token is kept in the browser's memory, not the server's.)

Latency budget (where the 300 ms goes)

Browser ─ network 40 ms ─► API auth+routing 5 ms ─► rules (pure) 1 ms ─► SQL 2 queries 20 ms ─► serialize 5 ms ─ network 40 ms
Total ≈ 110 ms. A 100 ms email call inside the request would be fine alone, but its failures and spikes are not → outbox.

CAP and consistency in simple words

When the network splits a distributed system you must choose: stay consistent (refuse some requests) or stay available (answers may be stale). The LMS is a single database: it keeps strong consistency for balances. Where staleness is fine (cached holidays) it accepts eventual consistency.

DataConsistency
Balance, request statusStrong (wrong value = wrong decision)
Holidays cacheEventual (seconds to hours old is fine)
Email deliveryEventual, at least once

Observability: the three pillars

Logs (what happened), metrics (how much, how fast), traces (where the time went, linked by traceId). The LMS puts traceId in every error body so a user report leads straight to a log line. Never log personal data.

Three required components each 99.5 % available. Combined?
Multiply: 0.995³ ≈ 0.985. More required parts, less availability.
