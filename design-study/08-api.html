API design

An API is a contract: send this, get that, including when things go wrong. Design it so a client cannot misuse it and an attacker learns nothing.

The ten LMS conventions

#RuleWhy
1Version in the path: /api/v1/...Visible, testable; breaking change = v2
2Plural nouns, kebab-case: /leave-requestsPredictable
3State changes are action sub-resources: POST /leave-requests/{id}/approveA status change has rules, balance effects, audit and email; it is not a field edit
4camelCase JSON, enums as stringsReadable
5Leave day "2026-11-10"; moment UTC "2026-10-19T14:52:00Z"A day is not a moment
6Caller comes from the token, never the bodyNo impersonation
7Authorization: Bearer <JWT>Same shape in Dev and Entra mode
8Lists: ?page=&pageSize= (max 100) → {items,page,pageSize,totalCount}Protects the server
9Idempotency-Key on creating POSTsDouble-click safe
10ETag on reads, If-Match on decisionsTwo managers cannot both decide on version 5

Walk through one call

POST /api/v1/leave-requests
Authorization: Bearer eyJ...
Idempotency-Key: 6f1c2d9a-3b7e-4c1a-9d52-0a8e41b7c9f3
{ "leaveTypeId": 1, "startDate": "2026-11-09", "endDate": "2026-11-13", "halfDay": "None", "reason": "Family function" }

201 Created
Location: /api/v1/leave-requests/101
ETag: "AAAAAAAAB9E="
{ "id": 101, "status": "Pending", "daysCount": 4.0, "availableAfter": 14.0, ... }

The body has no employeeId, status or daysCount: the server decides. A repeat with the same key and body returns the same 201; same key, different body returns 422 idempotency_key_reused.

Pick the status code

One error format: Problem Details + code + traceId

{ "type": "https://leave.example/errors/overlap", "title": "Dates overlap an existing leave",
  "status": 409, "code": "leave_overlap", "detail": "12 Nov is already covered by request 98.",
  "traceId": "00-4bf92f3577b34da6a3ce929d0e0e4736-00" }

The client switches on the stable code, not on wording. One global exception handler maps known failures and logs unknown ones; it never returns a stack trace.

Design principles (interview gold)

PrincipleLMS example
Never trust the clientAngular hides a button; the API re-checks role, ownership and rules
Ownership check on every idIds are small integers (guessable), so every handler loads "mine, or my report's, or I am HR"
Server computes, client displaysallowedActions in the response so Angular does not copy rules
Preview = same rule run twiceNo second copy of day counting in Angular
Expose what the screen needsResponses shaped for a use, not table copies
Contract toolingGenerate OpenAPI and a typed Angular client so drift breaks the build, not production

REST vs GraphQL vs gRPC

StyleChoose whenLMS
RESTResource-shaped data, fixed screens, easy caching and toolingChosen
GraphQLMany clients each needing different fieldsOne client; no
gRPCService-to-service, high throughput, streamingNo services to connect

Paging, filtering, versioning

  • Offset paging for page-number screens (max 100); keyset (cursor on Id) for big lists like audit.
  • Filtering and sorting run in the database using the screen's index.
  • Evolve without breaking: add fields, never rename or remove; a breaking change is /v2 served beside v1.

Practice: design the API for a new feature

"Employees can attach a medical certificate to a Sick request."

  1. POST /leave-requests/{id}/certificate (multipart, owner only) → 201; 404 if not yours; 422 file_type_not_allowed.
  2. GET /leave-requests/{id}/certificate → only owner, approver, HR (privacy: highest-risk upload); streams the file with a short-lived link.
  3. New table MedicalCertificate; retention one year after leave; audit each view.
Why POST /approve instead of PATCH status?
A status change is a business action, not a field edit.
409 or 422 for "not enough balance"?
409 is for clashes with current state that a reload may fix.
