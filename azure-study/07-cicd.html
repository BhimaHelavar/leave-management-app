CI/CD with GitHub Actions

CI (continuous integration) builds and tests every change. CD (continuous delivery) ships a tested build to Azure. Your repo already has CI (ci.yml, checks.yml). We add a deploy workflow.

The plan from spec T-02

  • .github/workflows/deploy.yml, trigger manual only (workflow_dispatch): you press a button, nothing deploys by accident.
  • It writes config.json with the Azure API URL, deploys the web, deploys the API.
  • Secrets come from GitHub Actions secrets. The SQL string is set in Azure, not in the workflow.

Secrets you need

GitHub secret / variableWhatHow to get it
AZURE_STATIC_WEB_APPS_API_TOKENDeployment token for the webaz staticwebapp secrets list …
AZURE_WEBAPP_PUBLISH_PROFILESimple option for the API: its publish profile (XML)az webapp deployment list-publishing-profiles -g $RG -n $API --xml
Variable API_URLhttps URL of the API (not a secret)Settings → Variables

Add them in GitHub: repo → Settings → Secrets and variables → Actions. Never echo them in logs.

deploy.yml (simple version, matches the spec)

name: deploy
on:
  workflow_dispatch:            # manual only

permissions:
  contents: read

jobs:
  api:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with: { dotnet-version: 10.0.x }
      - run: dotnet publish src/LeaveManagement.Api -c Release -o publish
      - uses: azure/webapps-deploy@v3
        with:
          app-name: ${{ vars.API_APP_NAME }}
          publish-profile: ${{ secrets.AZURE_WEBAPP_PUBLISH_PROFILE }}
          package: publish

  web:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 24, cache: npm, cache-dependency-path: web/package-lock.json }
      - run: npm ci
        working-directory: web
      - run: npm run build
        working-directory: web
      - name: Write runtime config for Azure
        run: echo '{"apiUrl":"${{ vars.API_URL }}"}' > web/dist/web/browser/config.json
      - uses: Azure/static-web-apps-deploy@v1
        with:
          azure_static_web_apps_api_token: ${{ secrets.AZURE_STATIC_WEB_APPS_API_TOKEN }}
          action: upload
          app_location: web/dist/web/browser
          skip_app_build: true
Not runThis YAML is a draft: I checked its syntax but never ran it. Action version numbers drift; check the action pages for the current major version. Pin third-party actions by version, and keep the checks.yml repo-guard that scans for secrets.

Better: log in with OIDC (no stored password)

A publish profile is a long-lived password. OIDC federation replaces it: GitHub proves to Entra "this run is workflow X of repo Y on branch Z" and receives a short-lived Azure token. Nothing to rotate or leak.

GitHub run ──(signed OIDC token: repo, branch, environment)──► Entra ID
Entra ID checks the "federated credential" you set up (issuer + subject match)
Entra ID ──(short-lived Azure access token)──► the run, which calls Azure with the role you granted

One-time setup

$APPNAME = "gh-lms-deploy"
$APPID = az ad app create --display-name $APPNAME --query appId -o tsv
az ad sp create --id $APPID
$SUB = az account show --query id -o tsv
az role assignment create --assignee $APPID --role Contributor --scope "/subscriptions/$SUB/resourceGroups/$RG"

# trust your repo's "production" environment
$cred = '{"name":"gh-prod","issuer":"https://token.actions.githubusercontent.com","subject":"repo:BhimaHelavar/leave-management-app:environment:production","audiences":["api://AzureADTokenExchange"]}'
$cred | Out-File cred.json -Encoding utf8NoBOM
az ad app federated-credential create --id $APPID --parameters cred.json
az account show --query tenantId -o tsv      # note it

Store AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_SUBSCRIPTION_ID as GitHub secrets (they are identifiers, not passwords, but keep them tidy).

permissions:
  id-token: write      # allows the run to request the OIDC token
  contents: read
jobs:
  api:
    runs-on: ubuntu-latest
    environment: production        # must match the federated credential subject
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v2       # check the current major version
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
      - run: az webapp deploy -g rg-lms-demo -n ${{ vars.API_APP_NAME }} --src-path api.zip --type zip
ErrorMeaning
"No matching federated identity record found"The subject in Azure does not match the run (branch vs environment vs pull_request). Match it exactly.
AuthorizationFailedLogin worked, but the service principal has no role on that scope
AADSTS700024Clock skew or expired assertion; re-run

Safe deploys: environments and approvals

A GitHub Environment named production can require a reviewer to click Approve before the job gets its secrets. Add it under Settings → Environments. Add concurrency so two deploys never run at once: concurrency: deploy.

Rollback

  • Redeploy the previous good commit by running the workflow on that commit (Use workflow from → tag).
  • With slots (Standard tier): swap back.
  • Database: migrations only add; test a restore plan before you need it.
