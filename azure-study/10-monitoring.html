Monitoring: know when it breaks

Logs tell you what happened, metrics tell you how much, traces tell you where the time went. Azure collects all three in one place.

The pieces

ServiceWhat it is
Azure MonitorThe umbrella: metrics, logs, alerts, dashboards
Log Analytics workspaceThe database where logs are stored and queried with KQL
Application InsightsMonitoring for your app: requests, exceptions, dependencies (SQL calls), timings. Stores its data in a Log Analytics workspace
Health checkAzure pings /health and replaces an unhealthy instance. The LMS already has /health

There is a small free monthly data allowance for Application Insights/Log Analytics ingestion (I believe about 5 GB, but I did not verify the current number; check the pricing page). Set a daily cap so a noisy log cannot cost money.

Turn it on for the API

az monitor log-analytics workspace create -g $RG -n log-lms-demo -l $LOC
$WSID = az monitor log-analytics workspace show -g $RG -n log-lms-demo --query id -o tsv
az monitor app-insights component create -g $RG -a ai-lms-demo -l $LOC --workspace $WSID --kind web
$CS = az monitor app-insights component show -g $RG -a ai-lms-demo --query connectionString -o tsv
az webapp config appsettings set -g $RG -n $API --settings "APPLICATIONINSIGHTS_CONNECTION_STRING=$CS"

The App Insights SDK must be in the app to send data. That is a NuGet package (Azure.Monitor.OpenTelemetry.AspNetCore) and one line in Program.cs: builder.Services.AddOpenTelemetry().UseAzureMonitor();. The LMS does not have it yet, and adding a package needs your approval, so I did not change code.

KQL: the query language

Read a query top to bottom; each | passes rows to the next step, like a shell pipe.

// the slowest API calls in the last hour
requests
| where timestamp > ago(1h)
| summarize calls=count(), p95=percentile(duration, 95) by name
| order by p95 desc

// failures per endpoint
requests
| where success == false
| summarize failures=count() by name, resultCode
| order by failures desc

// 403 spikes (your audited AccessDenied cases)
requests | where resultCode == "403" | summarize count() by bin(timestamp, 5m)

// exceptions with their message
exceptions | project timestamp, type, outerMessage | order by timestamp desc | take 20

Alerts

  • Alert on symptoms users feel: HTTP 5xx count, health check failing, response time p95.
  • Pieces: rule (condition) → action group (email / SMS / webhook).
az monitor action-group create -g $RG -n ag-lms --short-name lms --action email me you@example.com
$APPID = az webapp show -g $RG -n $API --query id -o tsv
az monitor metrics alert create -g $RG -n api-5xx --scopes $APPID --condition "total Http5xx > 5" --window-size 5m --evaluation-frequency 1m --action ag-lms

The three questions when something is wrong

  1. Is it up? curl /health. Database field says Unreachable → SQL (paused? firewall? string?).
  2. What error? az webapp log tail or the exceptions table.
  3. Since when? Compare with the last deploy time (GitHub Actions run history).
