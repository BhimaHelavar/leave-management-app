Configuration, secrets and identity

The golden rule of the LMS repo: no secret in git, ever. This page shows where secrets live instead, and how to remove passwords altogether.

Where a value should live

Kind of valueExampleWhere
Not secret, same everywhereLogging levelsappsettings.json
Not secret, differs per environmentAPI URL, allowed originApp setting / config.json
SecretSQL password, signing key, deploy tokenApp Service setting (ok for demo) → Key Vault (better) → no secret (best)

How .NET picks a value (precedence)

appsettings.json  <  appsettings.{Environment}.json  <  environment variables  <  command line
(later wins)       →  Azure App Settings ARE environment variables, so they override the files

Keys with : become __ in environment variables (Auth:Mode → Auth__Mode).

Level 1: App Service settings (what the demo uses)

  • Stored encrypted at rest, shown masked, injected as environment variables.
  • Anyone with Contributor access to the web app can read them. Good enough for a demo; weak for a team.

Level 2: Key Vault

Key Vault is a locked safe for secrets, keys and certificates, with an access log and versions. The app does not store the secret; it stores a reference.

$KV = "kv-lms-$SUFFIX"
az keyvault create -g $RG -n $KV -l $LOC --enable-rbac-authorization true
az keyvault secret set --vault-name $KV -n sql-conn --value "<connection string>"

# App Service setting that points at the secret instead of containing it:
az webapp config appsettings set -g $RG -n $API --settings "ConnectionStrings__Default=@Microsoft.KeyVault(SecretUri=https://$KV.vault.azure.net/secrets/sql-conn/)"

For this to work the web app needs permission to read the vault. That is where managed identity comes in.

Level 3: managed identity (no password at all)

A managed identity is a username Azure creates for your web app and keeps the password itself. Your code never sees a secret. Two kinds: system-assigned (tied to one resource, deleted with it) and user-assigned (separate, reusable).

Web app ──(asks Azure for a token as itself)──► Entra ID
Web app ──(token)──► Key Vault   "give me secret sql-conn"   ✔ if role Key Vault Secrets User is granted
Web app ──(token)──► Azure SQL   "log me in"                 ✔ if the identity is a database user
az webapp identity assign -g $RG -n $API
$PID_ = az webapp show -g $RG -n $API --query identity.principalId -o tsv
$KVID = az keyvault show -n $KV --query id -o tsv
az role assignment create --assignee-object-id $PID_ --assignee-principal-type ServicePrincipal `
  --role "Key Vault Secrets User" --scope $KVID
RBAC in one sentenceRole-based access control = who (identity) + what (role) + where (scope). Give the least role at the smallest scope.

Passwordless SQL (concept)

The web app's identity becomes a database user: CREATE USER [lms-api-bs92] FROM EXTERNAL PROVIDER; plus roles such as db_datareader/db_datawriter. The connection string becomes Authentication=Active Directory Default with no password. This needs an Entra admin on the SQL server. It is the right target design; for the first deploy the SQL login is simpler. I have not run this for the LMS.

Entra ID and the 4g milestone

Microsoft Entra ID (formerly Azure AD) is Microsoft's identity service. Today the LMS uses Auth:Mode=Dev (demo people, no password). In step 4g the API will accept real Entra tokens (Auth:Mode=EntraId).

Client secrets are secret. IDs are public. An Angular SPA uses PKCE and has no client secret.
