CORS in plain words

The browser refuses to let a page from origin A read a response from origin B unless B says "A is allowed". Origin = scheme + host + port. For a non-simple request the browser first sends an OPTIONS preflight; the API must answer with Access-Control-Allow-Origin: https://<swa-host> and the allowed headers (Authorization).

# test the preflight yourself
curl -i -X OPTIONS https://$API.azurewebsites.net/api/dev/token `
  -H "Origin: https://$WEBHOST" -H "Access-Control-Request-Method: POST" -H "Access-Control-Request-Headers: content-type"
CORS is not security for the APIIt only protects browsers. Anyone with curl can call the API. The real protection is authentication and authorization.

TLS and certificates

  • Azure gives every *.azurewebsites.net and *.azurestaticapps.net host a valid certificate.
  • Custom domains on Static Web Apps get free managed certificates. On App Service the Free tier cannot bind a custom-domain certificate; B1 and above can.
  • Set minimum TLS 1.2 and disable FTP deploys (already in the commands).

Static Web Apps trade-offIP restrictions on Static Web Apps need the Standard plan, so the static shell is public on Free. That is acceptable: it holds no data. The data sits behind the API, which needs a token.

Security checklist for the demo

Important riskAuth:Mode=Dev lets anyone who can reach the API pick any demo person, including Admin. On a public URL that means the demo data is open to anyone. Restrict the API by IP (spec T-02), or deploy only for short sessions, until Entra ID arrives in 4g.
