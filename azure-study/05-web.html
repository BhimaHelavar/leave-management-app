The Angular app on Static Web Apps

Your Angular build is only files (dist/web/browser). Static Web Apps stores them and serves them worldwide with free HTTPS.

What the Free plan gives (and does not)

You getYou do not get
250 MB app, free HTTPS, 2 custom domains, 3 staging environments, global CDNLinking your own App Service as /api (Standard plan), IP restrictions, SLA
Consequence for the LMSThe browser calls the API directly at its own URL, so the API must allow that origin (CORS), and Angular must be told the API URL at run time. That is exactly what config.json is for.

Step 1: create the app

$WEB = "lms-web-$SUFFIX"
az staticwebapp create -n $WEB -g $RG -l eastasia --sku Free
az staticwebapp show -n $WEB -g $RG --query defaultHostname -o tsv

Static Web Apps only exist in a handful of regions (the "location" is just where its management data lives; content is served globally). eastasia is the closest to India as far as I know; run az staticwebapp create -h to see the list.

Step 2: the runtime config contract

The app fetches /config.json before the first screen. Locally it is {"apiUrl":"http://localhost:5000","devStub":true}. On Azure the deploy step overwrites it:

{ "apiUrl": "https://lms-api-bs92.azurewebsites.net" }
  • apiUrl must be an absolute http(s) URL with no trailing slash or the app shows the config-error page.
  • Omit devStub on Azure.
  • Build once, run anywhere: no environment-specific build. Only this small file changes. Interview point: this is the twelve-factor "config in the environment" idea applied to a browser app.
Set-Content -Path web/dist/web/browser/config.json -Value ('{"apiUrl":"https://' + $API + '.azurewebsites.net"}') -Encoding utf8NoBOM

Step 3: staticwebapp.config.json (replaces nginx.conf)

Locally nginx gave you two things: the single-page-app fallback and a security-header policy. On Static Web Apps the same job is done by this file, placed in the app output folder (put it in web/public/ so Angular copies it to the build).

{
  "navigationFallback": {
    "rewrite": "/index.html",
    "exclude": ["/assets/*", "/*.{css,js,json,ico,png,jpg,svg,woff2}"]
  },
  "globalHeaders": {
    "X-Content-Type-Options": "nosniff",
    "Referrer-Policy": "no-referrer",
    "Content-Security-Policy": "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self' https://lms-api-bs92.azurewebsites.net; frame-ancestors 'none'"
  }
}
Two traps 1) Exclude config.json from the fallback (the *.json pattern above). Otherwise a request for it is rewritten to index.html and the app fails to parse it.
2) The old CSP says connect-src 'self' http://localhost:5000. On Azure it must name the API origin instead, or the browser blocks every API call. Start from the CSP in web/nginx.conf; the one above is a simplified example.

Step 4: build and deploy

cd web
npm ci
npm run build                      # output: dist/web/browser
cd ..
$TOKEN = az staticwebapp secrets list -n $WEB -g $RG --query properties.apiKey -o tsv
npx @azure/static-web-apps-cli deploy ./web/dist/web/browser --deployment-token $TOKEN --env production

The deployment token is a secret. Do not paste it into files. In CI it lives in a GitHub secret (next but one page). Installing the CLI through npx downloads a package; as per your rules, ask before adding anything to the project. Here it runs from the npm cache and does not change package.json.

Step 5: connect the two halves

  1. Copy the Static Web Apps host name.
  2. Set Cors__AllowedOrigin=https://<host> on the API (page 4) and restart: az webapp restart -g $RG -n $API.
  3. Open the site. The login screen should list the demo people. If it shows the config error page, check config.json in the browser's Network tab.

Custom domain (optional)

Add a CNAME from www.yourname.com to the default host name, then bind it in Portal → Static Web App → Custom domains. Azure issues a free certificate. DNS changes can take time.
