Azure SQL Database

A managed SQL Server. Azure does backups, patching and high availability; you own the schema and the data.

What it is and how the free offer works

  • Logical server (lms-sql-xyz.database.windows.net): the endpoint, admin login and firewall. Holds databases.
  • Database (LeaveManagement): where the tables live.
  • Serverless free offer: each month per database 100,000 vCore-seconds, 32 GB data and 32 GB backup. Only new databases qualify, up to 10 per subscription. No SLA.
  • Auto-pause: after 15 idle minutes the database pauses (no compute cost). The first query afterwards waits while it resumes. When the free seconds are used up, AutoPause pauses it until next month; BillOverUsage keeps it running and bills you, and cannot be undone. The LMS spec chooses AutoPause.
Do not leave SSMS or Azure Data Studio connectedAn open connection stops auto-pause and burns your free seconds. Close the tool when you finish.

Step 1: create server and database

$SUFFIX = "bs92"                       # your own 3-8 character unique text
$SQL    = "lms-sql-$SUFFIX"
$ADMIN  = "lmsadmin"
$PW     = Read-Host "SQL admin password (min 8, mixed)" -AsSecureString
$PWPLAIN = [Runtime.InteropServices.Marshal]::PtrToStringAuto([Runtime.InteropServices.Marshal]::SecureStringToBSTR($PW))

az sql server create -g $RG -n $SQL -l $LOC --admin-user $ADMIN --admin-password $PWPLAIN

az sql db create -g $RG -s $SQL -n LeaveManagement `
  --edition GeneralPurpose --family Gen5 --capacity 2 --compute-model Serverless `
  --use-free-limit true --free-limit-exhaustion-behavior AutoPause

# prove it is the free database:
az sql db show -g $RG -s $SQL -n LeaveManagement --query "{free:useFreeLimit, behaviour:freeLimitExhaustionBehavior, state:status}"
Check before you trustThe flag spelling comes from the repo's research file. Run az sql db create -h and compare. If the free offer is not available in South India, Azure says so; try Central India, then Southeast Asia, and move the resource group's other resources to the same region family. The first free database's region applies to all free databases in the subscription.

Step 2: the firewall (the most common first error)

The server rejects everyone by default. Error: Client with IP address … is not allowed to access the server. Open two doors:

# door 1: your laptop (to run migrations)
$MYIP = (Invoke-RestMethod https://api.ipify.org)
az sql server firewall-rule create -g $RG -s $SQL -n my-laptop --start-ip-address $MYIP --end-ip-address $MYIP

# door 2: Azure services (the App Service API). 0.0.0.0 is Azure's special "allow Azure" value
az sql server firewall-rule create -g $RG -s $SQL -n AllowAzureServices --start-ip-address 0.0.0.0 --end-ip-address 0.0.0.0
Security note"Allow Azure services" lets any Azure customer's service reach the server's front door; they still need the login. It is acceptable for a demo. The stronger design is a private endpoint or a managed identity login (see the Security page).

Step 3: the connection string

Server=tcp:lms-sql-bs92.database.windows.net,1433;Initial Catalog=LeaveManagement;User ID=lmsadmin;Password=<password>;Encrypt=True;TrustServerCertificate=False;Connection Timeout=60;
  • Encrypt=True is required on Azure. Connection Timeout=60 gives a paused database time to wake up.
  • Never commit it. It goes in App Service connection strings (see the API page). In .NET it arrives as ConnectionStrings:Default, which is what Program.cs reads.

Step 4: create the tables (the gap)

Why this step existsProgram.cs calls DatabaseInitializer.InitializeAsync(..., seedDemoData: true) only when app.Environment.IsDevelopment(). Azure uses Demo, so the API starts, /health may say the database is unreachable or empty, and every real call fails with "Invalid object name". You must create the schema yourself.

Option A: idempotent SQL script (the repo's decision, safest)

# from the repo root. "idempotent" = safe to run twice; it checks the migration history table
dotnet ef migrations script --idempotent `
  -p src/LeaveManagement.Infrastructure -s src/LeaveManagement.Api -o migrate.sql

# READ migrate.sql first. It is just CREATE TABLE statements.
sqlcmd -S lms-sql-bs92.database.windows.net -d LeaveManagement -U lmsadmin -P "<password>" -i migrate.sql

No dotnet-ef yet? Ask me before installing: dotnet tool install --global dotnet-ef (an install, so I did not run it). You can run the .sql in SSMS or the portal's Query editor too.

Option B: run the app once locally against Azure SQL

$env:ASPNETCORE_ENVIRONMENT = "Development"
$env:ConnectionStrings__Default = "<the Azure connection string>"
dotnet run --project src/LeaveManagement.Api
# Development => MigrateAsync + reference data + demo seed run once. Stop it with Ctrl+C.
Remove-Item Env:ConnectionStrings__Default

This also loads the demo people, balances and holidays in one go. Trade-off: it runs code against a remote database from your laptop and seeds demo data by design; fine for a demo, not for production.

Better long-term (a spec change, not done)Add an explicit setting like Database:SeedDemo=true so Demo can seed on purpose, without pretending to be Development. That is a small, reviewable change for a future task.

Check it worked

SELECT name FROM sys.tables ORDER BY name;                 -- your LMS tables
SELECT TOP 5 * FROM __EFMigrationsHistory;                 -- which migrations ran

Backups and restore (concept)

Azure keeps automatic backups (point-in-time restore for a short window). You restore into a new database, never over the old one. Know the words RPO (how much data you can lose) and RTO (how long to recover).

Why did Demo not create the tables?
See Program.cs: the initializer is inside if (app.Environment.IsDevelopment()).
The first query after a quiet hour is slow. Why?
Auto-pause saves free seconds; resume takes a few seconds to a minute.
