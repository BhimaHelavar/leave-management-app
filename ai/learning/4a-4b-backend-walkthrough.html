1. The four layers

What it is: one solution, four projects. How it works: a request goes inward through the layers; code may only depend inward. Press the button to watch one.

Why: business rules ("a balance never goes below zero") live in the centre and know nothing about SQL Server or HTTP, so you can test them alone and swap the outside. Trade-off: four projects is more ceremony than one; fine for a CRUD tool, worth it for real rules.
Where we are: only Domain and Infrastructure have real content. Application is an empty shell, Api has one endpoint.

3. Ledger plus balance

Like a bank: the ledger explains why, the balance answers how much. Press the buttons in order.

LeaveBalanceEntry (ledger, never edited)
TypeDaysNote
LeaveBalance.Available (fast copy)
0.0
CHECK: Available >= 0
Why two tables: the ledger is the audit history; the balance is a quick read. A reconciliation query (sum of ledger vs Available) detects any disagreement. Rejected: a single counter column, which cannot explain itself.

4. Overlap cannot happen

Rule 13: a person cannot have two leaves on the same half-day. LeaveRequestDay has one row per half-day with a unique index on (EmployeeId, LeaveDate, Slot).

Why in the database: a C# check "is there an overlap?" has a race window: both requests pass the check, then both insert. The unique index closes it. The code still checks first to give a friendly message.

5. Transactional outbox

How an approval triggers an email without ever losing it, or sending one for an approval that rolled back.

Why: if you sent the email inside the request, a crash between "email sent" and "saved" gives a phantom email; between "saved" and "email" gives a lost one. The outbox makes both facts commit together. ProcessedMessage makes the consumer safe if a message arrives twice.

6. What Program.cs does

Startup runs top to bottom; each request flows through the middleware in order. Step through it.

  1. Read Auth:Mode: must be "Dev" or "EntraId", else refuse to start (typo cannot silently disable auth).
  2. Read the one allowed CORS origin (the Angular app, no wildcard).
  3. Register ProblemDetails, CORS policy "web", AddApplication(), AddInfrastructure().
  4. Build the app. In Development only: migrate and seed the database.
  5. Middleware: exception handler, then status pages (errors become JSON with no stack trace).
  6. Middleware: security headers (nosniff, no-referrer, X-Frame-Options DENY).
  7. Middleware: CORS check.
  8. Endpoint GET /health (anonymous on purpose): checks the database, returns a DTO.
  9. app.Run(): the server starts listening on port 5000.
Known gaps spotted: Program.cs (/health) uses DateTimeOffset.UtcNow and DevSeeder.cs uses DateTime.UtcNow; the project rule says use TimeProvider so tests can fake the clock. Also the web page title is still "Web", and INDEX.md says 4c is at Requirements although design.md and tasks.md exist.

7. Why these choices, and what was rejected

ChoiceRejectedTrade-off
4 projects (Clean Architecture)One projectMore ceremony; rules stay independent
Enums as textEnums as intsA few more bytes; readable, safe to reorder
No cascade delete, soft deleteCascadeExtra IsActive checks; history survives
Overlap via unique indexC# check onlyOne extra table; no race window
DTOs over the wireReturn entitiesMore classes; no over-posting or leaks
Migrate at startup in Dev onlyAlwaysExtra deploy step; prod login needs no schema rights
Fluent API in InfrastructureAttributes on entitiesMore code; Domain stays free of EF

When to use or avoid

  • Clean Architecture: use when business rules are the valuable part; avoid for small CRUD.
  • Outbox: use when a DB change must reliably trigger a message; avoid if losing it is harmless.
  • Ledger table: use when you must explain a number; avoid for a plain counter.
  • Filtered / covering indexes: use for one hot known query; do not add on every column.

8. Interview Q&A

Try answering before opening.

1. Why Clean Architecture?

Business rules stay independent of database and web framework, so they are testable and the outside can be swapped. Cost: more projects.

2. How do you stop overlapping leave under concurrency?

A unique index on (employee, date, half-day slot). The database settles the race; a C# check alone has a race window.

3. Why a ledger and a balance table?

Ledger for audit and explanation, balance for fast reads, and a reconciliation query to compare them.

4. What is RowVersion for?

Optimistic concurrency: a stale update fails with DbUpdateConcurrencyException instead of silently overwriting.

5. Why store enums as strings?

Readable data, and reordering the enum cannot corrupt old rows.

6. Why no cascade delete?

Leave and audit history must survive. Use soft delete (IsActive).

7. What is the outbox pattern?

Save the message with the business change in one transaction; a worker sends it later. No lost or phantom messages.

8. Why migrate at startup only in Development?

Least privilege: the production app login should not be able to change the schema.

9. What is a filtered index?

An index over only rows matching a condition (for example Status = 'Pending'). Smaller and faster.

10. Why TimeProvider?

So tests can control the clock, for example to test a carry-forward expiry date.

9. Rebuilding this shape without AI

Practise the order of decisions, not the typing.

  1. Create the solution and four projects; reference only inward.
    dotnet new sln -n MyApp --format slnx
  2. Add Directory.Build.props (target framework, nullable, warnings as errors).
  3. Model Domain on paper first: nouns become classes, fixed choices become enums.
  4. Add EF Core SQL Server to Infrastructure; write the DbContext and one configuration per entity. For each rule ask: "can the database enforce this too?"
  5. Create the first migration, read its SQL, apply it.
    dotnet ef migrations add Initial --project src\MyApp.Infrastructure --startup-project src\MyApp.Api --output-dir Persistence\Migrations
  6. In Program.cs add DI, ProblemDetails, CORS, security headers and /health. Run it.
  7. Only then build features one use case at a time: DTO, validation, use case, endpoint, tests.
